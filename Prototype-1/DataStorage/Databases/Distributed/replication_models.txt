Replication models define how database copies are kept in sync.
Synchronous replication writes to replicas before confirming to client.
It guarantees strong consistency but increases write latency.
Asynchronous replication confirms writes immediately, replicating in background.
It offers low latency but introduces potential data loss.
Single-leader replication routes all writes through a master node.
The master node propagates changes to replica slave nodes.
Failover promotes a follower to leader if the master crashes.
Split-brain occurs if two nodes believe they are the active leader.
Multi-leader replication allows writes on several designated nodes.
It is useful for databases distributed across distinct datacenters.
Conflict resolution is required when replicas update the same row.
Leaderless replication accepts writes on any database node.
Clients write to multiple replicas concurrently to ensure quorum.
Read repair updates stale replicas when a client reads data.
Anti-entropy background processes compare replicas using Merkle trees.
Sloppy quorums allow writes to temporary nodes during partitions.
Hinted handoff stores updates until the target node recovers.
Replication lag is the delay between master write and follower update.
Read-after-write consistency ensures users see their own updates.
Monotonic reads guarantee users won't see data revert in time.
Consistent prefix reads ensure causal relationships are preserved.
Statement-based replication logs and executes SQL queries on replicas.
Write-ahead log (WAL) shipping replicates raw byte changes.
Logical log replication replicates row changes for database independence.
